## 3. 已完成或已有明确代码事实

### 3.1 公共只读人员能力

状态：**部分范围内已完成**。

已确认：

- `people/contracts.py` 已定义人员 DTO 和读取协议；
- `people/services.py` 已提供只读查询服务；
- `people/adapters/blog_author.py` 已将旧 `blog.Author` 映射为公共读取结果；
- 可以按 ID/slug 读取旧作者数据，而不要求上层直接了解旧模型字段。

限制：

- 这不是公共人员模型；
- 这不是公共写入和后台管理；
- 这不是 `PagePersonRole`；
- 这不是 BlogPage/GuidePage 已完成公共多对多关系。

### 3.2 公共只读资源能力

状态：**部分范围内已完成**。

已确认：

- `resources/contracts.py` 已定义资源 DTO 和读取协议；
- `resources/services.py` 已提供图片/文档等只读读取服务；
- `resources/adapters/blog_resource.py` 已兼容旧 Blog 资源模型；
- Markdown 行内图片已有公共读取入口；
- 旧资源模型仍保留，未做物理迁移。

限制：

- 目前主要是读取和映射，不代表资源上传、引用、导入、删除和 GC 已公共化；
- 不代表 Wagtail 全局图片/文档配置已切换；
- 不代表历史资源数据已经迁移。

### 3.3 搜索基础设施

状态：**部分范围内已完成**。

已确认：

- 搜索状态、Outbox、Delivery 和 Target 模型已经存在；
- 有生成代次、版本、租约、重试和旧事件保护等基础逻辑；
- 有 Elasticsearch 投影、Alias、重建和一致性检查相关代码；
- 有多组针对搜索模型、生产、投递、重建和正确性的测试文件。

限制：

- 当前信号生产者仍绑定 `BlogPage`；
- 文档构建、重建、范围重算、建议查询和结果回查仍直接使用 BlogPage 或 BlogPublicationState；
- `mongo_content_id` 仍然是搜索链路中的旧 Blog/Mongo 身份字段；
- 因此 GuidePage 不能只通过注册一个 Registry 就完整接入当前搜索生命周期。

### 3.4 BlogPage 旧生命周期

状态：**Blog 专用链路已存在，不属于本项目公共化完成项**。

已确认：

- `BlogPage.save()` 有 Mongo 正文保存逻辑；
- `BlogPage.publish()` 使用 `BlogPublicationService`；
- `BlogPage.unpublish()` 推进 Blog 发布代次并清理正式指针；
- `BlogPage.delete()` 依赖 Blog 删除保护和 Mongo 状态；
- Blog 导入、孤儿检查、删除任务和 Feed/详情服务仍存在。

这部分是当前系统的运行事实，也是后续解耦时必须保护的兼容基线。

## 5. 尚未进一步明确的决策

这些问题已经被识别，但仍不能在实现中自行决定。

### 5.1 Manifest 与字段版本

必须明确：

1. 一个 Wagtail Revision 是否对应一个 Manifest；
2. Manifest 是否包含多个字段条目；
3. `body` 和 `intro` 是否共享一个发布代次；
4. 字段是否拥有独立的内容版本号；
5. Codec、schema version、hash、长度和状态写在 Manifest 还是字段版本记录；
6. 单字段损坏或缺失时，是阻止整页发布，还是允许产品定义的部分降级；
7. 列表、Feed、详情、SEO 和搜索分别读取正式值还是预览值。

当前已明确的只有：`body` 与 `intro` 是两个独立字段身份，不能合并成一个无来源的 `content`。

### 5.2 GuidePage 字段存储

第一阶段暂定 `body` 外置到 MongoDB，其余字段先保留 MySQL，但还需要逐字段确认：

- 是否为关系字段；
- 是否参与 SQL 筛选、排序、权限或页面树查询；
- 是否属于长正文；
- 是否需要独立版本化；
- 是否进入搜索投影；
- 是否需要和正文一起恢复。

不能仅因为字段没有多对多关系，就推断它应放入 MongoDB。

### 5.3 `PagePersonRole` 关系

需要明确中间关系是否包含：

- `role`；
- `is_primary`；
- `sort_order`；
- `contribution_type`；
- 生效和失效时间；
- 页面类型专属元数据；
- 同一人员同一页面同一角色的唯一性。

### 5.4 搜索索引与投影

需要明确：

- 一个统一索引、多个页面类型索引，还是统一 Alias 下的多个物理索引；
- 页面类型、模型身份和字段策略如何注册；
- `body`、`intro`、标题和摘要的权重；
- 外置正文不可用时是否拒绝投影；
- 搜索删除墓碑保留多久；
- 索引重建期间的旧 Alias、代次和切换方式；
- 搜索分析是否记录页面类型、查询范围、结果数量和请求耗时；
- 查询文本、用户身份和 IP 等敏感字段如何脱敏或不保存。

### 5.5 搜索分析兼容策略

需要明确：

- 新分析事件是否与旧 `QueryDailyHits` 双读兼容；
- 是否需要停写切换；
- 去重身份和重复请求处理；
- 失败重试和保留周期；
- 历史统计是否迁移；
- Blog 与 Guide 的统计维度是否统一。

### 5.6 `resources` 是否拆出 `media`

当前确认 `resources` 是公共能力边界，但是否最终拆出独立 `media` 应用仍待后续依据部署、权限、资源生命周期和团队维护成本决定。此决策不影响第一阶段先建立 `resources` 公共接口。

### 5.7 旧数据迁移顺序

仍需明确：

- BlogImage、BlogDocument 和 Embed 的迁移顺序；
- Blog Markdown Batch、Token、Session、Artifact 的兼容读取和收敛方式；
- Author 到 Person/Role 的映射和冲突处理；
- 旧 Mongo 正文到 Manifest/字段版本的映射；
- 停写窗口、双读窗口和回滚点；
- 旧表、旧字段、旧索引和旧 API 的保留周期。

### 5.8 删除、引用、GC 与补偿

需要形成统一契约：

- 页面删除意图如何记录；
- 引用校验由 MySQL 关系、正文引用还是资源清单承担；
- Mongo/MinIO/Elasticsearch 的删除是否立即执行；
- 结果未知时如何查询；
- 墓碑、租约和补偿任务如何推进；
- 何时允许物理清理；
- 如何防止正在被其他页面引用的资源被 GC。

## 6. 当前最小实施顺序

按照风险最低、可回滚和不破坏 Blog 旧行为的原则，建议如下：

1. **冻结事实和协议**
   - 维护本审计文档和状态清单；
   - 完成页面能力矩阵、存储权威矩阵、依赖矩阵和兼容矩阵；
   - 把尚未明确的决策逐项变成可回答的问题。
2. **完善 `people`/`resources` 只读与引用接口**
   - 先不迁移模型；
   - 先让新页面业务代码只依赖公共接口；
   - 增加适配器和契约测试；
   - 保留旧 Blog 读取和后台行为。
3. **建立 `external_content` 最小框架**
   - 先定义字段身份、Codec、Manifest、版本和正式指针；
   - 先做 Blog 兼容读取；
   - 再为 GuidePage 写契约测试；
   - 不立即替换 Blog 生命周期。
4. **实现 GuidePage 最小页面**
   - 先确定字段清单和 `body` 外置契约；
   - 完成页面模型、权限、Revision、预览和发布边界；
   - 通过同一套外置内容协议接入。
5. **再公共化 `search`**
   - 引入 Registry、正式正文适配器和页面能力声明；
   - 将事件、投影、重建、删除和范围重算改为页面类型无关；
   - 完成 Blog/Guide 双页面重复、乱序、删除和权限测试。
6. **最后执行物理模型和历史数据迁移**
   - 先备份、演练、对账和回滚；
   - 再迁移 resources、people 和旧正文；
   - 最后切换全局配置、停写入口和旧模型兼容策略。
