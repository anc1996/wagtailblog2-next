## 1. 审查结论与相较原方案的变化

本次将原先偏重 Blog 业务拆分的说明，统一为 **Wagtail/Django 原生 CMS + 公共能力平台 + 内容类型注册 + 可选业务 App**。旧源码提供功能清单和风险证据，新站不继承旧库、旧模型或旧迁移链的约束。新站使用独立数据库及资源命名空间；旧数据导入另行立项。

相较修订前 09，新增或强化：

1. 原生页面树、栏目权限、Workflow、定时发布、复制、别名、移动、删除、历史比较及恢复的完整接入要求，不能只验手工发布。
2. 通用 Page 选择、卡片 Provider、动态 chooser 的服务端校验，以及 Home 跨类型人工轮播。
3. Blog/Guide 相关文章 InlinePanel、标签自动推荐、Gallery、正文轮播与可复用集合各自的 Revision 归属。
4. TopicPage、Series、FeaturedCollection 与栏目、taxonomy 的不同语义及更新传播边界。
5. Discovery 驱动的 Archive、Feed、热门与搜索；单一正式索引写入权威。
6. 资源实体、对象存储、媒体处理、文件交付与 Embed 分工；历史媒体引用保护。
7. WordPress 式声明注册与依赖倒置、第三种中立 Page 验收、插件版本及安全卸载边界。
8. 明确排除会员付费与在线插件市场；首次迁移前评估 User，不顺带建设商业权益系统。
9. 按任务及实际能力调度代理，移除全员固定流程、例行记忆写入、固定分钟数和无关三库快照要求。

本轮仅完成方案与治理层修订。所有 P0～P8 仍须按新站合同实施和验收。

## 2. 原生职责与公共扩展职责

| 职责 | 原生机制优先 | 需要补充的公共模块及限制 |
|---|---|---|
| 页面与栏目 | Page Tree、Site、Locale、Page 子类 | 类型注册、类型字段及模板；不造万能内容实体 |
| 编辑与发布 | Revision、预览、比较、恢复、Workflow、Tasks、排程、发布及撤销 | external_content 桥接完整 Manifest；不建立 Mongo 发布/审核系统 |
| 关系编排 | InlinePanel、Orderable、ParentalKey、Chooser | 通用 Page 选择、排序/去重/防自身、卡片 Provider、目标访问复核 |
| 可复用内容 | Snippet 及可选 Revision/发布/审核能力 | Series/Collection 建模和传播策略；不能假设普通 Snippet 自动版本化 |
| 用户与后台 | Django User/Group/Permission、Wagtail 栏目及 Collection 管理权限 | 公共 Access 与资源交付校验；后台权限不替代前台授权 |
| 资源 | 原生图片/文档模型、rendition、chooser、Collection | 公共资源实体、引用与历史保护、MinIO Storage、Range/签名交付 |
| 搜索 | 原生搜索接口及后端扩展 | 正式快照 Projection/Outbox/重建；界定原生自动写入范围 |
| 实时业务 | Django 普通关系及后台扩展 | 评论、反应、统计独立记录，不进入 Page Revision |
| 可选扩展 | Django App、Wagtail Hooks、Panels、Blocks/ViewSets | 类型化同步接口及事务后事件；不允许任意 Hook 改写正式权威 |

没有外置字段的 Page 不需要 Mongo 或虚构的 Manifest。只修改标题也形成新的原生 Revision，完整 Manifest 可以复用未变字段的不可变版本。SQL 回滚后的 Mongo 预写数据保留待对账，不物理删除补偿。

## 4. 必须修正的架构倾向

- 旧 Blog 发布状态、公共读取包装和模型替身不能被当成新站公共平台；应明确注册装配层与公共接口，公共服务不反向导入业务 Page。
- 不用一个万能关系表覆盖父 Page 内联、正文块、独立集合与访客评论；它们的 Revision 所有者不同。
- 不重复开发 Wagtail 生命周期。原生删除可能删除 Revision，不能承诺“页面删除后所有历史仍可恢复”；删除前需要与 Page 外键级联无关的 tombstone/资源保护证据及保留策略。
- ReferenceIndex 不能自动发现全部 Markdown、Mongo Manifest 或历史引用。资源回收必须覆盖这些来源，并单独授权。
- 全链路访问校验不能只在卡片渲染时检查；搜索摘要/高亮/建议/计数、Feed、缓存和对象交付也要覆盖。
- 不以“学习 WordPress”为由建设插件市场、任意热装卸、万能 Metadata 或一套会员支付模型。
- 不重复建立 Registry：公共类型身份与能力配置是基线，各模块注册其专属 Provider/Codec/消费者；不得各自定义不一致的公开资格。

## 5. App 依赖与 P0～P8 调整

Python 依赖方向为 **业务 Page / 可选 App → 公共协议 → Django/Wagtail 基础**。启动装配层可以引用具体类型进行注册，公共服务通过协议调用，不倒向 Blog。Archive 只消费 Discovery；Home/Portfolio/Topic 消费 Selection/Card；评论/统计引用普通 Page；Search/Feed 使用正式读取及 Access；AI 使用公共任务引擎和类型策略；import 使用类型装配及资源摄取。

阶段表详见 [02](02-统一外置内容与公共能力项目管理路线图.md)。P0 提前确定身份、权限、Registry/Selection 和初始资源迁移图，P1 维持公共图片独立交付；P2 分媒体编辑器/人员分类，P3 分外置快照/完整生命周期；P4 分正式 Page/内容编排；P5 集中发现归档搜索与热门；P6 导入/AI，P7 实时互动及前台对账，P8 第三种 Page、容量与恢复。

这样安排防止首次迁移后才发现 User/Document 模型不兼容，也避免在 P0 一次实现全部 CMS。P1 使用两个真实 SQL 测试 Page，不冒充正式 Blog/Guide，不引入 Mongo/ES。

### 11.2 迁移路线的推荐与未证明假设

**推荐 B。**在原仓库内建立明确的新站配置及自有模型边界，复用纯公共代码；必要时使用新的自有 App label，保留 Django/Wagtail/第三方 label 和迁移。这样能将旧 Blog 的模型、Hooks、信号及迁移依赖一起隔离，避免只替换迁移目录却仍装载旧业务。不复制整个项目，也不为了复用旧模型牺牲新站独立性。
