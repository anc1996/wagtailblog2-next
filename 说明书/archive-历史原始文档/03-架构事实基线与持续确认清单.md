## 1. 已确认事实

### 1.1 Git 与生产

- 生产路径：`/home/source/Django/wagtail/wagtailblog3`。
- 生产分支：`main`。
- 生产 `HEAD` 与本地 `origin/main` 一致。
- 新分支：`feature/unified-external-content-search`。
- 新分支基于生产 `main` 创建。
- 生产工作树只有未跟踪环境备份文件，没有源码修改。
- 本地新分支存在协作配置同步变更，但 `wagtailblog3` 运行时代码尚未修改。

证据类型：代码/Git 事实。

### 1.2 应用目录与分支差异

生产和 `origin/main` 当前存在：

```text
archive

blog
comments
content_ai
home

```

生产和 `origin/main` 当前不存在：

```text
guides

```

当前特性分支相对生产/main 已新增：


但这两个应用目前只是无迁移的公共读取契约与 Blog 兼容适配层，不等于人员模型、资源模型或资源生命周期已经迁移完成。

当前特性分支仍不存在：

```text
guides
external_content
```

因此，`GuidePage`、公共 Manifest、统一外置内容发布状态和统一外置内容协调器仍属于目标设计，不是当前代码事实。

证据类型：生产/main 与当前特性分支的代码差异核对。

### 1.3 Search

当前 Search 已包含：

- SearchState；
- SearchOutbox；
- SearchDelivery；
- SearchIndexBuild；
- alias 切换；
- rebuild；
- consistency check；
- retry/lease；
- Wagtail 搜索分析菜单。

但仍存在 Blog 耦合：

- 发布/撤销/删除信号使用 BlogPage；
- 正文 Delivery 查询 BlogPage；
- 正文构建依赖 BlogPublicationState；
- bootstrap 只初始化 BlogPage；
- API 只识别 `blog` 类型；
- 搜索结果格式化对 BlogPage 特判；
- SearchAnalytics 使用没有内容类型维度的 QueryDailyHits。

证据类型：代码事实。

### 1.4 Author

当前 Author 仍位于 `blog.models`，关联 `blog.BlogImage`，BlogPage 通过 ParentalManyToManyField 关联；作者列表、详情、Feed、API、缓存和关系查询仍主要位于 Blog 应用。

当前特性分支新增的 `people` 仅提供 `PersonRecord`、读取协议、Blog Author 适配器和公共读取服务；尚未创建公共 `Person`、`Role` 或 `PagePersonRole` 模型，也尚未切换现有 Blog 调用方。

证据类型：代码事实。

### 1.5 媒体与资源

当前 Blog 应用包含：

- BlogImage；
- BlogRendition；
- BlogDocument；
- Markdown/代码/Mermaid/表格/Embed Block；
- 音频和视频 Block；
- 多种第三方 Embed Finder；
- Markdown 导入 Batch/Token/Session/Artifact；
- 远程媒体下载、MIME 探测和清理补偿。

Wagtail 图片、文档和 Embed 配置仍指向 Blog 模型或 Blog Finder。

当前特性分支新增的 `resources` 仅提供图片/文档读取 DTO、读取协议、Blog 兼容适配器和公共读取服务。Markdown 行内图片预览已有一个调用方优先使用 `resources.get_image_by_id()`，但上传、引用、导入会话、清理、回收和补偿仍未公共化。

证据类型：代码事实。

## 2. 已确认决策

1. BlogPage `body` 外置到 MongoDB。
2. BlogPage `intro` 外置到 MongoDB。
3. 所有外置页面统一使用公共外置内容协议。
4. Wagtail Page 生命周期是唯一页面生命周期入口。
5. 搜索服务公共化，BlogPage、GuidePage 和未来页面共用。
6. 搜索分析公共化，不再只按 BlogPage 设计。
7. Author 拆为公共人员能力。
8. 图片、文档、音频、视频、Embed、上传和导入拆为公共资源能力。
9. 旧 Blog 数据兼容读取，新写入统一公共协议。
10. 上线前停写切换，不做长期在线双写。
11. 删除、回收和 GC 使用公共协议。
12. `2E-1e-2 = BLOCKED-FACTS`。

证据类型：用户确认的产品决策。

## 4. 需要项目经理持续追踪的问题

### 4.1 命名决策

- 公共人员应用命名已确认：`people`。
- `Author` 是作者角色或历史兼容别名，不再作为 Blog 专属模型。
- 公共资源/内容导入能力当前按 `resources` 规划；是否进一步拆出独立 `media` 应用，仍待部署、权限和生命周期证据确认。
- Search Registry、Projection、Outbox、Delivery 和搜索分析均归入公共 `search` 应用；具体内部模块目录仍待协议设计确认。

### 4.2 数据契约

- BlogPage `intro` 的 Mongo Codec 和 schema version。
- GuidePage 外置字段完整清单。
- Manifest 的字段身份格式。
- Revision 与 Mongo version 的一一对应规则。
- 正式正文指针存放位置。
- 外置正文缺失时前台、后台和搜索的具体响应。
- 旧 `BlogPublicationState` 的兼容读取截止时间。
- 旧 `mongo_content_id` 的兼容读取优先级。

### 4.3 搜索分析

- 是否建立新的搜索请求事件表；
- 是否按 `model_label`、`content_type` 或 `search_type` 作为主维度；
- 零结果以请求时结果数量记录，还是异步查询索引后推导；
- Blog/Guide/全站搜索是否共享物理 ES 索引；
- 搜索分析数据保存周期和隐私脱敏规则。

### 4.4 People 与资源迁移

- `Author` 历史模型名和表名如何作为兼容层保留；
- 人员简介 `bio` 是否属于外置正文，还是继续保留 MySQL；
- 作者头像是否使用公共资源模型；
- 未来讲师和贡献者是否与公共人员共用一张人员表；
- BlogImage/BlogDocument 是否长期保留为兼容模型；
- Markdown 导入旧 Batch、Token、Session、Artifact 如何归入 `resources` 的公共导入模块；
- 历史正文中的资源引用如何对账。

### 4.5 生命周期与删除

- Workflow 审批 Revision 是否始终作为发布目标；
- 直接发布和 Workflow 是否共享同一个公共校验入口；
- 页面删除是否先写删除意图；
- Mongo 版本和媒体资源的最短保护期；
- 回收失败时的重试、人工介入和恢复方式。
