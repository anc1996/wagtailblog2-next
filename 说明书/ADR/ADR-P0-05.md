# ADR-P0-05：最小自定义 User 与展示人员身份分离

- 日期：2026-10-31
- 状态：最小 AbstractUser 与 P0-DEV-01 身份标识已批准；迁移与兼容性待验证。
- 证据级别：E2 无外部 IO 身份装载已验证；无用户记录、认证或后台测试结果。
- 用户批准：`site_identity.User` 技术方案已确认；独立技术审查：本切片待复核。

## 来源与用户已确认

依据旧参考仓库 `说明书/00-产品需求与项目管理/` 的 00、04 U10/U11/U20/U26、08、09 §10.2/§14.1、10 §14。10 较早章节“默认 User 或自定义 User 待选”的历史描述已被 U26 更新，不能继续据此要求用户重选。

确认内容：继承 AbstractUser，保留 Django/Wagtail 原生认证、用户组和权限；首版不加会员、支付、订阅或业务资料字段。Person 是作者/讲师等展示身份，按需关联 User 不自动赋予后台编辑或前台阅读权限。

本轮用户已明确批准 `site_identity`、`AUTH_USER_MODEL="site_identity.User"` 和最小 `AbstractUser` 的 P0-DEV-01 实现范围；这不等于迁移、后台认证、权限或真实服务验收。Sol 不自行验收。

## 方案建议：最小身份契约

| 项目 | 候选值或边界 | 状态 |
|---|---|---|
| 根包/AppConfig | `wagtailblog2.apps.identity.apps.IdentityConfig` | 已批准并实现 |
| 模型身份 | `site_identity.User` | 已批准并实现 |
| 设置 | `AUTH_USER_MODEL="site_identity.User"` | 已固定；首次迁移前不得改名 |
| 模型基类 | Django AbstractUser | 已确认并实现 |
| 初始迁移 | `site_identity.0001_initial` 创建 User | 技术建议，图与状态待验证 |

首版不自创认证协议、角色表或权限权威，不默认改邮箱为登录名，不引入头像、电话、会员状态、套餐或个人业务档案。保留继承的原生字段/管理器/认证行为；若未来要改变用户名/登录标识、唯一性或身份绑定，必须另行决策，不能作为普通字段补丁执行。

项目关系用选定的可交换 User 标识，运行时解析按框架支持方式；不硬编码 `auth.User` 或旧 Blog 的人员模型。实际形式须在获授权实现时审阅，本文不是运行代码。

## Person、owner 与权限分责

1. Person 拥有公开姓名/简介/展示角色等领域职责，不作为登录用户替身；具体 Person 模型及 label 另审，不在首版 User 里预置其业务字段。
2. 作者、讲师、审核展示标签不等于原生权限或 Workflow 组；Person 也不等于 Page.owner。
3. 页面作者/讲师等编辑关系随父 Page/版本化 Snippet 的原生 Revision 保存；访客评论/反应/统计是独立实时数据。
4. 可编辑不等于可发布，可读不等于可编辑；资源 Collection 管理许可不自动赋予受限文件阅读权。操作合同见 [ADR-P0-08](ADR-P0-08.md)。
5. 账号停用与 Person 展示/历史引用如何关联留业务决策，不用删除账号级联抹除内容署名；实际关系策略与个人数据处理另行批准。

## 初始迁移与兼容性边界

User 必须在所属 App 的首个迁移中创建，不先按默认 auth.User 建库再替换。User 初始迁移不得反依赖 resources、home 或 Page；头像/人员等潜在循环关系放后续设计及迁移。

组/权限关系所需 auth 依赖以实际生成状态与 loader 为准；旧 09 中 auth.0012 是特定安装版本候选，不是通用固定边。自定义 User 的自有字段演进应维护自有迁移，不假设 auth 后续迁移替它更新字段。

Wagtail 用户管理表单、认证、组/权限、Collection 上传者、后台任务身份及第三方引用均须验证。继承声明、模型可导入或反向关系无冲突不能替代真实认证/后台证据。

## 风险与依赖

依赖 [ADR-P0-03](ADR-P0-03.md) 的持久标识、[ADR-P0-06](ADR-P0-06.md) 的设置一致性、[ADR-P0-07](ADR-P0-07.md) 的首迁移图。主要风险是先迁移默认身份、后期更换 label、User→资源→User 循环、将署名身份当审核资格，以及误把最小自定义 User 扩为会员系统。

## 验证计划、停止与回退

- E1：核对 U26 已确认/具体标识待批的分界，检查八份 ADR 中 User 引用一致。
- E2：在获批实施范围内，项目导入前阻断 DB、网络、Storage、任务和子进程，受守卫检查 swappable 解析、已有初始节点、groups/user_permissions、所有反向关系及模型状态；不创建用户、不生成或执行迁移、不连真实服务、不开展 E3。
- E3：另获空库和后台验证授权后，验证迁移、用户创建/编辑/登录/禁用、组/页面/Workflow/Collection 权限及真实上传者关系；不以假身份略过权限验收。
- 停止：已有默认 User 历史、身份标识未定、循环或关系冲突、认证方式/身份绑定需求扩大。
- 回退检查：迁移前修订候选；迁移后不通过改设置切回 auth.User、不删用户/权限/迁移历史。保存现状并单独评审恢复方案，具体数据操作须另授权。
