**目标：** 让 BlogPage、GuidePage 和未来 Page 通过公共协议复用人员、资源、外置正文、搜索和导入能力，逐步消除对 `blog` 的隐式依赖。

**架构：** 采用“接口先脱离、生命周期后统一、物理模型最后迁移”的路线。第一阶段保留旧模型和旧表作为兼容后端，仅将上层依赖改为公共接口；跨存储发布、搜索、删除和回收契约稳定后，才进行物理迁移。

**技术栈：** Django 5.2.8、Wagtail 8.0、MySQL 8.4、MongoDB/pymongo 4.11、Redis 5.2、Elasticsearch 8.19、Celery 5.5。

**依据：** `说明书/00-产品需求与项目管理/01-统一外置内容与公共能力产品需求基线.md`、`03-架构事实基线与持续确认清单.md`、`05-当前代码现状审计与公共能力解耦重构边界.md`。

## 全局约束

- 不在 `main` 分支直接开发、提交或推送；当前工作区分支必须先核对。
- 未经用户明确授权，不连接生产、不执行迁移、不批量回填、不物理删除、不重命名生产表。
- MySQL 页面元数据、Revision 和发布状态仍是页面生命周期权威；MongoDB 只承载声明为外置的不可变内容版本。
- Redis 只能承担缓存或协调职责；Elasticsearch 是可重建搜索投影，不能反向覆盖权威数据。
- 跨存储失败、超时、重复、乱序和结果未知必须有查询、对账、补偿和回滚边界。
- 每个阶段必须独立测试、独立验收、独立回滚；未通过当前阶段门禁不得进入下一阶段。

## 1. 总体策略

本方案不采用“先搬模型、再修引用”的大迁移方式，而采用四层逐步脱离：

```text
第 0 层：事实与契约冻结
        ↓
第 1 层：公共接口/适配器脱离，旧数据和旧模型不动
        ↓
第 2 层：页面能力和生命周期脱离 Blog
        ↓
第 3 层：物理模型、设置、数据写入和旧入口迁移
```

每一阶段都必须有独立的测试和回滚点。没有完成当前阶段的验收，不进入下一阶段；不允许为了“看起来已经公共化”提前删除旧 Blog 路径。

### 1.1 四个必须分开的概念

| 概念 | 含义 | 本方案中的处理 |
|---|---|---|
| 代码位置脱离 | 新能力代码不再放在 `blog` | 第 1 层开始做 |
| 依赖方向脱离 | 公共能力不再导入 `blog` | 第 1～2 层完成 |
| 数据模型脱离 | 表、模型、关系迁移到公共应用 | 第 3 层做 |
| 生命周期脱离 | 保存、发布、删除、搜索不再由 Blog 特判控制 | 第 2 层完成 |

“把文件移动到 `people` 或 `resources`”只解决第一项，不能单独宣称完成脱离。

## 2. 推荐优先级：先简单、后危险

### 优先级 0：现状矩阵和公共协议

这是所有编码前的准备阶段，不修改运行时代码。

必须建立四张矩阵：

1. 页面能力矩阵：BlogPage、GuidePage 和未来示例 Page 的字段、Revision、发布、撤销发布、删除和恢复入口；
2. 存储权威矩阵：MySQL、MongoDB、Redis、Elasticsearch 各自保存什么、何时可读、何时可写；
3. 依赖矩阵：所有 `blog` 导入、全局设置、信号、任务、管理命令、模板标签和测试；
4. 兼容矩阵：旧表、旧字段、旧 Mongo 文档、旧索引和旧 API 的读取与停写计划。

本阶段输出不是代码，而是字段级和入口级契约。未确认的内容标记为“待决策”，不允许在实现中隐式决定。

### 优先级 1：先做无迁移的公共接口脱离

这是第一个实际编码阶段，也是最简单、风险最低的脱离。

先不移动 `Author`、`BlogImage`、`BlogDocument`，不改 Wagtail 全局媒体设置，不创建迁移，不改生产表。新增公共服务接口和适配器，让上层开始依赖公共接口，而不是直接依赖 Blog 模型。

建议先做两个只读/引用型入口：

- `people`：人员读取、角色和页面关联查询的公共接口，第一版内部仍由 `blog.Author` 适配；
- `resources`：图片、文档、Embed 和资源引用的公共接口，第一版内部仍由 Wagtail 当前 Blog 模型适配。

此阶段的成功标准不是“模型已经搬走”，而是：新增页面业务代码只依赖 `people`/`resources` 的接口，不再导入 `blog.models.Author` 或 `blog.blocks.BlogDocument`。

### 优先级 2：统一 external_content 页面能力

在公共接口稳定后，再统一 BlogPage 和 GuidePage 的外置正文能力。

目标是让页面声明：

- 自己有哪些外置字段；
- 每个字段如何序列化和读取；
- 当前 Revision 如何绑定 Manifest；
- 哪个版本是正式发布版本；
- 字段缺失、损坏、超时和结果未知时如何失败关闭。

BlogPage 先通过适配器接入，不立即删除旧 `BlogPublicationState` 和旧 Mongo 流程。GuidePage 与 BlogPage 必须通过同一组合同测试。

### 优先级 3：搜索生命周期公共化

external_content 页面能力统一后，搜索才能脱离 Blog 特判。

改造方向：

- 监听 Wagtail 通用页面生命周期；
- 通过 Search Registry 判断页面是否可搜索；
- 通过页面正式正文适配器读取内容；
- Outbox、Delivery、墓碑、权限范围和生成代次不再识别 `BlogPage`；
- 搜索分析记录页面类型和内容类型。

### 优先级 4：物理迁移 resources 和 people

只有适配器已经稳定、历史读路径已验证，才做实际模型归属迁移。

推荐先迁移 `resources`，再迁移 `people`：

- resources 迁移影响全局 Wagtail 图片/文档设置和大量外键，属于高风险但边界较清晰；
- people 迁移影响作者 Feed、页面关系、后台管理和历史 URL，需要先完成角色关系设计。

### 优先级 5：Markdown 导入公共化

导入依赖页面字段映射、资源引用、权限和外置正文协议，因此最后处理。否则会把旧 Blog 专属假设重新带回公共架构。

## 4. 阶段 1：people/resources 无迁移适配层

### 4.1 目标

让未来页面从第一天开始依赖公共能力接口，即使底层暂时仍是 Blog 模型。

### 4.2 people 第一版边界

第一版只做读取和关系表达，不迁移数据：

- 定义人员查询接口；
- 定义角色值，如 author、instructor、contributor、editor、expert、reviewer；
- 定义页面人员关系查询结果，至少包含 person、role、is_primary、sort_order；
- 提供 Blog 兼容适配器，将当前 `Author` 映射成公共人员结果；
- 保留现有作者详情、Feed 和旧 URL，通过适配器调用旧查询；
- GuidePage 先可以接入公共接口，但不立即创建新的关系字段。

不在第一版做：

- 不迁移 `Author` 表；
- 不改 `BlogPage.authors` 的数据库字段；
- 不创建 `PagePersonRole` 迁移；
- 不删除旧 Author 查询。

### 4.3 resources 第一版边界

第一版只做资源引用和解析接口：

- 定义图片、文档、Embed 和远程媒体的统一资源引用 DTO；
- 定义资源解析、校验和引用发现接口；
- 将当前 `BlogImage`、`BlogDocument` 和 Blog block 作为兼容后端；
- 新的公共导入/页面服务只调用 resources 接口；
- 保留 Wagtail 当前全局图片/文档模型设置。

不在第一版做：

- 不修改 `WAGTAILIMAGES_IMAGE_MODEL`；
- 不修改 `WAGTAILDOCS_DOCUMENT_MODEL`；
- 不重命名物理表；
- 不移动已有 StreamField block；
- 不运行数据迁移或批量回填。

### 4.4 阶段 1 验收

必须证明：

1. 新增的公共服务不导入 `blog.models` 作为接口定义；
2. Blog 适配器可以在不改变旧行为的情况下返回公共 DTO；
3. GuidePage 或测试用 Page 可以调用同一接口；
4. 旧作者详情、旧图片/文档后台和旧 Blog 页面测试不回归；
5. 适配器缺少数据时返回明确的空值/不可用状态，而不是伪造资源或草稿内容。

### 4.5 回滚

阶段 1 只有新增接口和调用方替换。若失败，撤回调用方到旧 Blog 服务即可，不涉及表、Mongo 文档或全局 Wagtail 设置。

## 5. 阶段 2：external_content 统一页面协议

### 5.1 目标

让 BlogPage 和 GuidePage 共享同一个外置字段生命周期。

### 5.2 必须先确定的契约

- 字段身份采用 `page_type + field_name`，禁止把 `intro` 和 `body` 拼成一个不可区分内容；
- 一个 Wagtail Revision 对应一个 Manifest，Manifest 包含多个字段条目；
- 发布指针必须能定位到页面、Revision、字段、内容版本和生成代次；
- 草稿只允许后台预览读取，公开读取只允许正式指针；
- Mongo 写入失败、MySQL 回滚或网络超时时保留不可变版本，进入待对账/回收状态，不在异常处理中物理删除；
- 单字段缺失是否阻止整页发布，必须按页面类型声明，不能由通用代码猜测。

### 5.3 实施顺序

1. 为 GuidePage 固化公共协议合同测试；
2. 为 BlogPage 增加兼容适配器，读取旧 Mongo 正文；
3. 建立 Blog/Guide 双页面的保存、草稿、发布、撤销发布、删除和恢复测试；
4. 加入 generation/fence，拒绝旧事件覆盖新正式指针；
5. 对账通过后，才评估废弃 `BlogPublicationState`。

### 5.4 回滚

保留 Blog 旧读路径和旧发布状态；新协议失败时停止新写入入口，但不删除已有 Mongo 版本和 MySQL 状态。

## 6. 阶段 3：搜索公共化

### 6.1 目标

搜索只依赖页面能力和正式正文适配器，不依赖 BlogPage 类型。

### 6.2 具体边界

- `search.signals` 不再把 BlogPage 作为唯一生命周期 sender；
- Registry 决定页面是否进入搜索；
- Projection 通过页面适配器获得标题、摘要、正文和资源/人员索引字段；
- Outbox 事件至少包含 page_id、page_type、revision_id、generation、operation 和 idempotency_key；
- Delivery 拒绝旧 generation、旧 revision 和旧 schema 事件；
- 未发布、权限受限、撤销发布和删除页面不得进入公开索引；
- 搜索分析事件必须包含页面类型，并保留旧统计兼容读取方案。

### 6.3 验收

至少覆盖重复事件、乱序事件、迟到事件、Outbox 重放、Redis 故障、ES 不可用、权限变化、页面移动、复制、别名、翻译、删除和恢复。

## 7. 阶段 4：resources 物理迁移

### 7.1 前置条件

- 阶段 1 的公共资源接口已被页面和导入调用；
- 已统计 `BlogImage`/`BlogDocument` 物理表、外键、引用和后台权限；
- 已有隔离环境备份、迁移演练和回滚脚本；
- 已确定保留旧模型别名或代理模型的过渡周期。

### 7.2 推荐迁移方式

1. 新建公共模型或公共应用模型，但先映射既有物理表；
2. 让 Wagtail 配置在隔离环境切换到公共模型并执行系统检查；
3. 对旧 Blog 引用做双读校验；
4. 只在兼容读取和后台操作验证通过后切换新写入；
5. 保留旧导入路径的只读兼容期；
6. 最后才考虑旧模型和旧表的清理。

禁止一步完成：移动模型、修改设置、创建迁移、回填数据、删除旧模型。

## 8. 阶段 5：people 物理迁移

### 8.1 前置条件

- 已确认 Person、Role、PagePersonRole 的字段和唯一约束；
- 已确认作者旧 URL、Feed、后台筛选和页面展示兼容；
- 已完成 BlogPage、GuidePage 和未来示例页面的关系测试；
- 已确定旧 `Author` 表的只读保留期。

### 8.2 推荐迁移方式

1. 建立公共 Person/Role 表和旧 Author 映射；
2. 先双读校验，不立即双写；
3. 停写窗口内完成关系回填和计数对账；
4. 切换公共关系为新写入权威；
5. 旧 Author 只读兼容；
6. 作者详情、Feed、侧栏和搜索确认无回归后，再评估清理。

## 9. 阶段 6：Markdown 导入公共化

### 9.1 目标

将“Markdown 解析”和“创建哪一种 Page”分离。

### 9.2 分层

- 解析层：Markdown、图片、文档、Embed、链接和代码块识别；
- 资源层：调用 `resources` 创建或匹配引用；
- 字段映射层：由页面类型声明 Markdown block 到字段的映射；
- 页面服务层：由具体 Page 类型负责权限、父页面、字段校验和保存；
- 外置内容层：由 `external_content` 负责正文版本和 Manifest；
- 会话层：负责幂等、重试、失败产物和结果未知查询。

第一阶段只支持 BlogPage 和 GuidePage 的显式映射，不根据页面类名或字段名自动猜测。

## 11. 第一批只做什么

用户确认本方案后，第一批只执行阶段 0，不直接改 BlogPage、GuidePage、Author、媒体设置、搜索信号或数据库。

阶段 0 完成并确认矩阵后，第二批只做阶段 1 的一个最小切片：建议先做 `people` 只读适配器或 `resources` 资源引用接口中的一个，不同时做两套物理迁移。

推荐首个编码切片：`people` 只读适配器。原因是它不触碰 Wagtail 全局模型设置、不触碰 Mongo 生命周期、不触碰搜索 Outbox，也能立刻验证“未来页面不再直接依赖 Blog 模型”的依赖方向是否成立。

首个切片明确不做：

- 不创建数据库迁移；
- 不移动 `Author`；
- 不改 `BlogPage.authors`；
- 不改 BlogPage 发布、复制、删除和搜索流程；
- 不连接生产；
- 不提交到 `main`，不推送。
